# knowops 桌面端入库（desktop-ingest）

> 本文件是 knowops 的桌面端入库流程。执行前先加载 `references/workflow.md`
> （流程规范）与 `references/redlines.md`（操作规范与红线），并按其中约定读取
> `.config/agent-rules.md`。本文件只定义"内容 → 00 收件箱"这一步。
>
> 随身端条目由 everywhere-note 生成；字段契约（`type`/`created`/`tags`/标题）
> 需与其 SKILL.md 保持一致，任何修改须两端同步。**随身端稳定原则**：契约只含
> 内容型字段，不含桌面库结构信息（模块编号、路径、归属指向），随身端不做任何
> 入库判断——桌面端结构怎么改，都不反向要求随身端发版或重装。
> 旧格式条目不拒收：含可解析 frontmatter 的走「规范条目」通路（补全/修正字段，
> 不改变用户原文信息；历史字段如 `capture_kind` 照读不依赖、缺失不补）；
> 无 frontmatter 的才按「非规范文本」包装。
> GitHub 暂存库目录约定（`<知识库目录>/` 根目录放待入库条目、`归档/` 子目录
> 放已入库源文件）同样两端同步。

## 适用场景

用户要求入库，例如：

- "入库今天手机记的"（配置了 GitHub 暂存库时，自动拉取暂存库中的新条目）
- "把这段暂存文字存进知识库"（并粘贴文本或 md 块）
- "把这份 md 文件入库"（并提供文件）

桌面端直接说"记一下……"不属于本部分职责，按 `references/workflow.md` 处理。

## 来源与优先级

收到入库指令后按以下顺序处理；**本地 00 收件箱是写入目标，不是检查来源**：

1. **用户直接提供的内容**（文本 / md 块 / 文件）→ 逐条解析入库；
2. 用户未提供内容，且配置了 GitHub 暂存库（`.config/knowops.config.json` 的
   `githubSync`）→ 按「GitHub 暂存库拉取」拉取新条目入库；
3. 两者都没有 → **询问用户**（要收什么内容 / 是否配置 GitHub 暂存库），不静默空跑。

## 输入形态

一次可接收：一段或多段纯文本 / 规范 md 块（含 frontmatter）/ md 文件；
支持批量，逐条解析、逐条入库。

## GitHub 暂存库拉取（可选，配置了 githubSync 时执行）

1. **能力判断**：agent 自行判断平台具备的 GitHub 能力（gh CLI / git / GitHub MCP
   等，任一可用即可）；不具备时跳过本部分并如实说明。
2. **读取配置**：`githubSync` 的 `repo` / `branch` / `folder`（本库在暂存库中的
   目录名）。
3. **列出新条目**：列出暂存库 `<folder>/` 根目录下的 md 文件（排除 `归档/`
   子目录）；没有新文件 → 本部分结束，不写入、不移动。
4. **逐条拉取**：下载每个文件内容，按「解析与校验」处理（非规范内容包装为
   capture 条目）。
5. **写入 00 收件箱**：按「写入 00 收件箱」执行（相似检查照常）。
6. **归档源文件**：每条入库成功后，把暂存库中的源文件移动到
   `<folder>/归档/<入库当日日期>/`（日期格式 `YYYY年MM月DD日` 中文补零，与知识库
   归档约定一致；目标目录不存在则先创建）。本地 04 归档 不重复存放源文件。
7. **失败处理**：下载 / 写入 / 移动任一失败 → 如实告知用户，失败条目保留原位
   （下次入库可重试），不假装完成。

## 解析与校验

1. **切分条目**：以 `---` 起始的 frontmatter 或 `# 标题` 标题行识别新条目边界，
   每条独立处理；条目文件含 BOM/前导空白时先去除再解析。
2. **规范条目**：校验 `type: capture`、`created`、`tags`、标题；
   - 缺字段时补全：`created` 用收到时刻，`tags` 缺省 `[]`；
   - 历史字段（如旧版随身端的 `capture_kind`）照读不依赖、缺失不补——它不
     影响去向判定；
   - 格式修正（如 `tags` 改为行内数组）不改变用户原文信息；
   - 旧版随身端的日期前缀标题等老格式同样按本流程解析，不拒收。
3. **非规范文本**：包装为 capture 条目——`created` 用收到时刻，标题自动概括，
   正文保留原文，不精简用户提供的信息。
4. **相似检查**：每条写入前搜索 `00 收件箱` 是否存在高相似条目（同日 / 同标题 /
   内容高度重合；`待审阅-*.md` 不是内容条目，不参与相似检查）；发现疑似重复时
   **询问用户**：合并 / 跳过 / 仍写入。

## 写入 00 收件箱

1. **平铺写入根目录**：收件箱＝config `preferences.modules` 中 type=capture
   的登记模块目录（默认 `00 收件箱/`，无子目录，不按分类路由）；
2. 文件名 `序号-标题.md`：序号＝现有**`数字-` 开头 md 文件**的最大序号＋1
   （`待审阅-*.md` 与用户手写文件不计入序号），两位补零，超 99 自动三位；
   标题取条目标题（去掉日期前缀等旧格式痕迹）；
3. 用 Obsidian CLI 创建（路径/名称以配置与 `.config/agent-rules.md` 为准）；长内容或特殊
   字符按 `references/redlines.md` 的直写例外规范处理；
4. 写入后**回读校验**（批量入库优先用库内脚本 `vault_check.py check` 输出每篇
   键值摘要并抽 1 篇全文回读，见 `references/workflow.md`「操作后流程」；
   收件箱条目在脚本中输出 `[EXEMPT]` 摘要——豁免的只是必填/枚举**判定**，
   摘要扫读与全文回读照做），确认内容与结构正确；
5. **待审阅文件**：创建/追加当日 `00 收件箱/待审阅-YYYY-MM-DD.md`（一批入库
   一份、同日追加；列出本批入库条目与路径，开头注明「审阅后可删除本文件」，
   frontmatter 带 `type: capture`；规则见 `references/workflow.md`
   「写入审计闭环」）；
6. 在当日日记（Daily notes 约定的当日文件）agent 章「**入库**」小节追加详细
   记录（条目、路径、来源；格式见 `references/workflow.md`「日记」）。

## 汇总反馈

完成后向用户汇总：共入库 N 条（其中 GitHub 暂存库拉取 M 条）、每条路径、
补全/修正了什么（如有）、暂存库源文件归档位置、待审阅文件位置（审阅后可删）。
可提示下一步："审阅收件箱"进行沉淀（去向按用户手册「模块规则」判定：归属
模块 / 归档 / 删除 / 保留）按 `references/workflow.md` 处理。

## 边界

- 本部分只负责**收集入库 + 审计闭环（日记与待审阅文件）+ 汇总反馈**；
- 收件箱审阅、沉淀、删除、归档由用户在电脑端发起时按 `references/workflow.md`
  处理；
- 不设置任何提醒（电脑端不设提醒）。
