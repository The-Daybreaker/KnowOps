# 知识库管理工作流规范（workflow.md）

> 本文件是 knowops 的流程规范（reference）：描述知识库应当如何组织、各模块的流程
> 应当怎么走，供用户与 agent 共同查阅。工具无关，任何执行方式均适用。
> 通用红线见 knowops SKILL.md；执行层红线见 `references/redlines.md`。
> 红线与流程冲突时：高风险操作（大规模影响文件、永久删除等）先征求同意；
> 低风险的流程内操作先执行，随后记录、告知用户并给出回退方案。
>
> 初始化、插件集成、配置与 HTML 导出见 `references/init-config.md`。

所有目录名与文件名规则均为**可配置默认值**（见 `.config/knowops.config.json`），
实际以用户确认的配置为准。

## 知识库模型

- **两道门**：任何记录请求先过两道门，再谈流程——
  1. **归宿门**：这条内容在库外有没有更合适的家？待办有待办软件、项目文件有
     项目文件夹、可执行资产有它所属的仓库——有更合适的家就**不进库**，必要时
     在其所属处留一句指针即可。动机：有真家的内容在库里永远是影子副本，要付
     同步成本，还会过时。
  2. **形态门（兜底）**：内容必须能被 md 原生承载——化约成「一页读的东西」。
     脚本、可执行模板这类形态由模块准入条件在架构上挡住（见下），此处只兜底。
- **模块路由**：过了两道门的内容，简短、零碎、临时、说不清的先进 `00 收件箱`；
  明确的摘录直达 `02 摘录`；经验结论类进 `01 知识`。**捕获时不做分类判断**——
  分类只发生在沉淀时（内容已完整躺在面前）。动机：实测连 agent 在捕获时也常
  分错，分类的时机在沉淀，不在捕获。
- **稳定核心 + 可插拔模块**：一级模块长期稳定；新增模块须**同时满足五个条件**：
  内容有足够规模、有独立生命周期、有独立工作流、**可 md 原生承载**（答得出
  「它化约成一页读的东西是什么」）、**符合用户心智**（能用一个词说清装什么，
  写入与查找都顺日常直觉，不要求用户背规则）。编号顺延至系统之前。
- **目录不承担全部导航**：文件夹只负责"放在哪里合理"；动态导航依靠标签、
  属性、双向链接、根目录看板与 agent 整理。

## 规范与配置的边界

知识库约定分两层，改动方式不同：

| 层 | 内容 | 改动方式 |
|---|---|---|
| **规范层**（固定） | 模块编号规则与「系统、归档固定末两位」；两道门与模块准入五条件；宽进严出（规范只约束 agent、用户手写零要求、收件箱校验豁免）；先单体涨破再拆；记录质量把关；短篇「分类聚合 + 超量拆分」机制；归档按日期切分机制（含中文补零日期格式 `YYYY年MM月DD日`） | 属于 skill 内置规范；改动即破坏性变更，须升级 skill 版本并附说明 |
| **配置层**（可配置默认值） | preferences 全部目录名；日记日期格式（默认按年切分）；模板目录；导出开关与位置；githubSync 参数；看板视图集合（可增改）；短篇四分类集合（默认 名言/警句/思考/摘抄，可经确认扩展）；长篇分类文件夹集合（用到才建，可扩展） | 用户确认即改：agent 更新 `.config/knowops.config.json` 并记入 `03 系统/变更记录.md` |

> 与规范层冲突的配置（如把归档移出末两位、改用其他归档日期切分格式）不被支持。

## 模块总览（默认，可配置）

| 模块 | 职责 | 内部结构 |
|---|---|---|
| 00 收件箱 | 捕获入口：没想清楚的先放这里 | 平铺，无子目录 |
| 01 知识 | 验证过的经验与结论 | 主题文档（起步一份通用示例） |
| 02 摘录 | 抄来收藏的 | 长篇 / 短篇 |
| 03 系统 | 库自己的痕迹和说明书 | 日记 / 模板 / 看板.base / 用户文档 |
| 04 归档 | 不再活跃但保留的内容 | 按归档日期文件夹（如 `2026年08月09日/`） |

另有根目录 `看板.md`（库的正门，一屏总览），嵌入 `03 系统/看板.base` 的视图；
看板不是模块，不参与编号。

> **编号规则**：一级目录全部带数字前缀；**系统、归档固定位于末两位**（归档
> 殿后），未来新增模块插入其前并顺延编号。
>
> **懒加载**：初始化预置 03 系统（用户文档、模板）与 01 知识（示例主题文档），
> 并创建根目录看板；其余模块（收件箱、摘录、归档）首次写入时自动创建；
> 空文件夹在文件树中不显示。
>
> **移动目标目录**：把文件移动/归档到尚不存在的目录时，先创建目标目录再移动。

## 03 系统（用户文档与设施）

- **用户文档**：`用户手册.md`（一份总的用户手册：库的布局、怎么记、怎么整理、
  怎么找、记录质量参考——按人的认知规律编排，通俗易懂）、`变更记录.md`
  （结构变更历史）——共 2 份**用户可见、可编辑**的文档。
- **来源**：初始化为本库创建（来源本 skill `assets/system-manage/`），
  **目标已存在则绝不覆盖**（询问后决定保留或合并）。
- **模板**：`03 系统/模板/` 存放供 Obsidian 模板功能使用的笔记模板（见
  `references/properties.md` 与「01 知识」）；初始化复制并引导启用模板功能。
- **看板**：`看板.md` 固定根目录、`看板.base` 固定 `03 系统/`；新模块建立时
  看板同步增补视图。
- **日记**：见下文「日记（＝操作记录）」。
- **agent 读的个性化约束**（插件规则、额外红线、额外操作、旧库约定）统一存于
  `.config/agent-rules.md`，不在 03 系统；变更操作前读取（见 SKILL.md 红线 7）。
- **维护**：结构变更时更新用户手册相关部分并写入 `变更记录.md` 与当日日记。

## 模块流程

### 00 收件箱（捕获入口）

- **形态**：平铺，无子目录。文件名 `序号-内容简述.md`；序号＝当前收件箱最大
  序号＋1，两位补零，超 99 自动三位。沉淀后序号稀疏属正常，不回压重编
  （重编会断引用；序号只承担「到达顺序」一个职责）。
- **写入两条路**：
  - **agent 写入**：全套规范照做（属性与命名见 `references/properties.md`），
    为用户浏览时一眼可读；
  - **用户手写**：零要求——无属性、无序号、名字随手起都行。
  这就是**宽进严出**：规范约束的对象始终是 agent，不是用户的动作；门槛不长在
  用户这一侧。
- **校验豁免**：收件箱是校验豁免区，用户手写文件永不判「不合格」。校验是
  出门（沉淀）时的事。
- **审阅沉淀（严出，用户发起）**：逐条过，去向由内容定——
  1. 摘抄类 → `02 摘录`；
  2. 经验/结论类 → 合并进 `01 知识` 对应主题文档；
  3. 不再活跃 → `04 归档/<归档当日日期>/`；
  4. 无价值 → 删除（进系统回收站）；
  5. 仍不明确 → 留下。
  沉淀时补全：缺 `created` 用文件系统创建/修改时间，缺标签类型按内容补；
  沉淀后删除原收件箱文件（流程内变更，按红线 2 执行）。
- 随身端与暂存库条目的入库见 `references/desktop-ingest.md`。

### 01 知识（验证过的）

- **定位**：跨项目验证过的经验与结论（晋升而来），以及用户主动收录的理解类
  内容。**按主题组织**——一个主题一份文档；不按用途或抽象程度分类。动机：
  主题轴是用户真实的心智轴，写入与查找都不需要背规则。
- **起步**：初始化创建一份**通用示例主题文档**，自解释用法；用户可改名、删除
  或替换为自己的主题。
- **文档形状**：属性载体是主题文档本身；条目是文档内的小节——
  「章节（`##`）→ 条目（`###`，一句可直接执行的结论做标题）→ 正文（写清结论、
  动机与背景，可选一行来源小注）」。写入时提炼一层（不存对话原文），但信息量
  不压缩（见「通用操作规则 · 记录质量把关」）。
- **章节/主题命名**：名字自解释就不加说明（如「架构设计规范」）；不自解释的，
  标题下一行补使用场景（如「用户提示词规范」下一行：这是给用户设计提示词的
  时候用的）。判据：光看名字能不能知道什么时候用。
- **条目合并**（含晋升进库的条目）：收到条目与主题 → 创建前相似检查（红线 5）
  → 有该主题文档则找到章节合并（章节没有就加），没有主题文档则新建 → 日记
  记录、核验。条目晋升的时机与判据在库外（项目侧）定义，本库只管接收合并。
- **新建主题**：低风险，直接建，随后记录并告知用户。
- **章节涨破拆分（先单体、涨破再拆）**：单章条目超过约 30 条时，提议把该章
  拆成独立文档，原主题文档升级为同名文件夹收留——文件夹内主文档保留其余章节，
  顶部列出拆出的章节文档链接作导航入口。拆分涉及移动文件，**先展示方案、征得
  同意后执行**。这是全库唯一的生长方式，不提前设计层级。
- 旧知识系统的领域二级目录与按篇数的增长规则已废除。

### 02 摘录（抄来收藏的）

- **定位**：已成型的"收藏品"——外部摘抄（诗词、文言、名言警句等）与自己已成
  型的单句感悟；**未成型的想法（灵感）不进本模块**，仍走 00 收件箱。
- **两种形态**：
  - `长篇/`：诗词、文言等有完整篇幅的作品，**一篇作品一篇笔记**；分类文件夹
    （诗词 / 文言 / 文学（小说、名著）/ 网络）**用到才建**，可扩展（新增分类
    经用户确认）；
  - `短篇/`：名言、警句等短句摘抄，**按分类聚合**（初始每类一个文件：
    名言 / 警句 / 思考 / 摘抄），条目持续追加到文件末尾。
- **短篇分类约定**（固定四类）：`名言`（名人名言，有明确作者）、`警句`
  （警示格言，作者常不详）、`思考`（自己的单句感悟，出处可省）、`摘抄`
  （其他短句兜底）。
- **超量拆分**：短篇任一分类文件超过 **100 条**后，该分类由文件变为文件夹——
  原文件移入并改名 `<分类>/<分类> 01.md`，新开 `<分类>/<分类> 02.md`，此后
  新条目写入**序号最大**的文件，再超量继续顺延新开。
- 命名与属性见 `references/properties.md`（excerpt 条目）。
- **捕获**：桌面端明确说"摘录：……"时直达本模块（长篇建笔记 / 短篇追加聚合
  文件，写入前相似检查照常）；随身端摘录经 `00 收件箱` 审阅沉淀。
- **感想区**：笔记内含可选「感想」小节（个人理解与体会）。
- 摘录可归档（通用规则）。

### 04 归档

- 所有模块（收件箱、知识、摘录等）都可归档；
- 文件夹按**归档当日日期**命名：`2026年08月09日/`（中文补零）；
- 单篇文件平铺；文件夹整体归档时保留原文件夹名；
- **懒加载创建**：首次归档时先创建 `04 归档/<归档日期>/`（目标目录不存在时
  先创建再移入），归档后即可见；
- GitHub 暂存库同步入库的源文件归档在暂存库 `<folder>/归档/<入库日期>/`
  （见 `references/desktop-ingest.md`），本地归档不重复存放；
- 归档动作记入当日日记与 `03 系统/变更记录.md`。

## 日记（＝操作记录）

- 位置：`03 系统/日记/YYYY/YYYY-MM-DD.md`（**按年切分**，可配置）；
- **写入/修改/移动/删除/归档后追加一行**（`<时间> [类型] 动作与目标`，见
  「操作后流程」）；读取与搜索不记；
- 日记就是库的操作记录，由 agent 自动维护，用户不需要写，随时可以翻——它回答
  「某天我对这个库做了什么」；
- 日记**不参与看板聚合、不参与 HTML 导出**；
- 日志与日记是同一个文件，不存在两者同步的问题。

## 操作后流程（每次写入 / 修改 / 移动 / 删除 / 归档后执行）

1. 写日记：在当日日记追加一行（`<时间> [类型] 动作与目标`）；
2. 建立双向链接：沉淀/归档/相关笔记之间建立链接；
3. 插件规则：按 `.config/agent-rules.md` 中配置的规则执行（如版本提交、同步）；
4. HTML 镜像导出（若配置 `exportEnabled=true`）：写入/修改 → 单篇导出；
   删除/移动 → 全量导出（含清理）；
5. 看板反映确认：看板已启用时确认实时反映正确；
6. **核验**（结构面与语义面）：
   - **结构面**（属性可解析、必填属性、type 枚举、命名）：优先运行库内
     脚本 `vault_check.py`（见 `references/init-config.md` 「脚本一览」），
     扫读其输出的每篇键值摘要；**收件箱路径豁免、非 md 文件跳过**；脚本不可用
     时人工回读。批量写入（≥3 篇）时脚本核验全部条目并抽 1 篇全文回读；
     单篇写入仍全文回读；
   - **语义面**（内容正确性、双向链接指向、日记记录、插件规则与 HTML 导出
     执行情况）：由 agent 逐项核对；
   - 发现缺失立即补正并告知用户；
7. 反馈：写入位置、建立的链接、后续建议。

## 通用操作规则

- **写入前健康检查**：要写入某个既有文档（主题文档、短篇聚合文件等）时，
  先扫一眼全文，发现不符合规范的现象（多为用户手改痕迹），**先问用户「要不要
  先按规范整理，再写入新内容」**——不默默代改，也不踩着乱处直接写。
- **点名整理**：用户明确指出某文档动过、需要整理时，直接执行；库是 git 仓库
  时可用其差异信息辅助识别用户改动（不代为初始化仓库的红线不变）。
- **记录质量把关**（一切写入与入库的内容要求）：详实通俗——写清前因后果、
  背景与动机，保证用户看懂；不刻意追求专业性，为看着专业牺牲通俗是不应该的；
  不为省字写得过简；必要时用正常的日常化举例、比喻；**不精简用户提供的信息**，
  禁止「一句话说明白」式压缩——一句话本身就很难说明白；语言质量要高，无 AI 味
  （怪异比喻、不常见表达与举例一律不用），保证很久以后读来仍能充分理解。
  「提炼一层写入」指形式上提炼成可执行的结论，**信息量不压缩**。
- **兼容容忍**：用户自建的白板（`.canvas`）等非笔记文件是用户的自由空间——
  不主动整理、不校验、不导出、不报错；用户要求操作时按相应工具规范执行。
