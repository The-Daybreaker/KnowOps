# 知识库管理工作流规范（workflow.md）

> 本文件是 knowops 的流程规范（reference）：描述知识库的**通用机制**——两道门、
> 宽进严出、模块登记、审计闭环、日记与操作后流程，供用户与 agent 共同查阅。
> 工具无关，任何执行方式均适用。
>
> **各业务模块的具体规则（装什么、怎么入库、怎么分类、怎么命名）的唯一事实
> 来源是库内 `03 系统/用户手册.md` 的「模块规则」章节**——本文件不定义任何
> 具体业务模块，agent 执行入库、分类、整理时以手册为准，以库中实际存在且
> 已登记的文件夹为准。
>
> 通用红线见 knowops SKILL.md；执行层红线见 `references/redlines.md`。
> 红线与流程冲突时：高风险操作（大规模影响文件、永久删除等）先征求同意；
> 低风险的流程内操作先执行，随后记录、告知用户并给出回退方案。
>
> 初始化、插件集成、配置与 HTML 导出见 `references/init-config.md`。

目录名与日记格式均为**可配置默认值**（见 `.config/knowops.config.json`），
实际以用户确认的配置与登记为准；文件命名规则见各模块约定与
`references/properties.md`。

## 知识库模型

- **两道门**：任何记录请求先过两道门，再谈流程——
  1. **归宿门**：这条内容在库外有没有更合适的家？待办有待办软件、项目文件有
     项目文件夹、可执行资产有它所属的仓库——有更合适的家就**不进库**，必要时
     在其所属处留一句指针即可。动机：有真家的内容在库里永远是影子副本，要付
     同步成本，还会过时。
  2. **形态门（兜底）**：内容必须能被 md 原生承载——化约成「一页读的东西」。
     不合格内容由模块登记时的准入判据在架构上挡住（见下），此处只兜底。
- **模块路由**：过了两道门的内容，简短、零碎、临时、说不清的先进 `00 收件箱`；
  明确的内容按**用户手册「模块规则」**判定归属模块。**捕获时不做分类判断**——
  分类只发生在沉淀时（内容已完整躺在面前）。动机：实测连 agent 在捕获时也常
  分错，分类的时机在沉淀，不在捕获。手册规则覆盖不了的内容，问用户（不猜）。
- **通用地基 + 扩展模块**：skill 预置的基础模块只有四个（收件箱、知识、系统、
  归档，见「基础骨架」）；摘录等业务模块都是**登记的扩展模块**。新增模块 =
  用户在库里新建文件夹 → agent 发现未登记目录 → 问清规则 → 写进用户手册
  （见「模块发现与登记」）。模块登记时以**准入五条件**把关：内容有足够规模、
  有独立生命周期、有独立工作流、**可 md 原生承载**（答得出「它化约成一页读的
  东西是什么」）、**符合用户心智**（能用一个词说清装什么，写入与查找都顺日常
  直觉，不要求用户背规则）。
- **目录不承担全部导航**：文件夹只负责"放在哪里合理"；动态导航依靠标签、
  属性、双向链接、根目录看板与 agent 整理。

## 规范与配置的边界

知识库约定分两层，改动方式不同：

| 层 | 内容 | 改动方式 |
|---|---|---|
| **规范层**（固定） | 编号规则与「系统、归档固定末两位」；两道门与模块准入五条件；模块登记/注销机制；宽进严出（规范只约束 agent、用户手写零要求、收件箱校验豁免）；先单体涨破再拆；**原话完整**与记录质量把关；写入审计闭环（日记两章节＋待审阅文件）；归档按日期切分机制（含中文补零日期格式 `YYYY年MM月DD日`） | 属于 skill 内置规范；改动即破坏性变更，须升级 skill 版本并附说明 |
| **配置层**（可配置默认值） | preferences 全部内容（modules 模块清单、日记目录与格式、模板目录）；导出开关与位置；githubSync 参数；看板视图集合（可增改） | 用户确认即改：更新 `.config/knowops.config.json` 与库内本体（`看板.base`），并记入 `.config/变更记录.md` |
| **库内本体**（模块规则） | 各业务模块的规则：职责、入库规则、分类规则、命名约定，以及模块内部的分类集合、拆分阈值等 | 唯一落点是**用户手册「模块规则」章节**（用户确认即改，agent 登记/变更时写入）；config `preferences.modules` 只存机器索引（目录名/type），与手册由同一次登记流程写入 |

> 与规范层冲突的配置（如把归档移出末两位、改用其他归档日期切分格式）不被支持。

## 基础骨架（默认，可配置）

| 模块 | 职责 | 内部结构 |
|---|---|---|
| 00 收件箱 | 捕获入口：没想清楚的先放这里 | 平铺，无子目录 |
| 01 知识 | 验证过的经验与结论 | 主题文档（起步为空） |
| 02 摘录 | 扩展模块（预置示例，见手册） | 规则见用户手册摘录节 |
| 03 系统 | 库自己的痕迹和说明书 | 日记 / 模板 / 看板.base / 用户手册 |
| 04 归档 | 不再活跃但保留的内容 | 按归档日期文件夹（如 `2026年08月09日/`） |

上表是**默认骨架**：00–02–04 中只有收件箱、知识、系统、归档是基础模块，
摘录是预置登记的扩展模块（初始化时询问是否启用；不启用则不建目录、不登记，
手册中的摘录节保留作为「模块规则怎么写」的示例）。之后新增模块一律走登记，
编号顺延至系统之前。

> **编号规则**：一级目录全部带数字前缀；**系统、归档固定位于末两位**（归档
> 殿后），未来新增模块插入其前并顺延编号。用户自建的文件夹登记时由 agent
> 建议保持末两位的编号方案并征得同意后执行；用户坚持自己的编号则以用户
> 为准（结构校验会提示与规范不一致）。
>
> **懒加载**：初始化预置 03 系统（用户手册、模板）并创建根目录看板；
> 01 知识、收件箱、归档首次写入时自动创建；已登记扩展模块的目录
> 以实际存在为准（目录消失走注销问询，见「模块发现与登记」）；
> 空文件夹在文件树中不显示。
>
> **移动目标目录**：把文件移动/归档到尚不存在的目录时，先创建目标目录再移动。

另有根目录 `看板.md`（库的正门，一屏总览），嵌入 `03 系统/看板.base` 的视图；
看板不是模块，不参与编号。模块登记/注销时看板同步增补/移除对应视图。

## 03 系统（用户文档与设施）

- **用户手册 = 单一事实来源**：`用户手册.md`（模块规则 + agent 约束 + 布局 +
  怎么记 + 怎么整理 + 怎么找 + 质量参考 + 注意事项）。**用户可见、可编辑，
  同时是 agent 的必读规则来源**——agent 执行入库、分类、整理前先读其
  「模块规则」与「agent 约束」两章（见 SKILL.md 前置第 4 步）。
- **来源**：初始化为本库创建（来源本 skill `assets/system-manage/`），
  **目标已存在则绝不覆盖**（询问后决定保留或合并）。agent 修改手册仅限：
  模块登记/注销、经用户确认的规则变更、用户明确要求；不做其他改写。
- **变更记录**：库的结构与规则变更史在 `.config/变更记录.md`——低频文件不占
  用户可见空间，由 agent 在结构/规则变更后追加（含原因与依据），人可随时在
  文件管理器中查看；结构变更时同步更新用户手册相关部分。
- **模板**：`03 系统/模板/` 存放供 Obsidian 模板功能使用的笔记模板（见
  `references/properties.md` 与「01 知识」）；初始化复制并引导启用模板功能。
- **看板**：`看板.md` 固定根目录、`看板.base` 固定 `03 系统/`；模块登记/注销时
  看板同步增补/移除视图。
- **日记**：见下文「日记（＝操作记录）」。
- **agent 约束**（插件规则、额外红线、额外操作、旧库约定）统一存于用户手册
  **「agent 约束」章节**（v3.0.2 起并入手册，`.config/agent-rules.md` 废除；
  旧库遗留的该文件走现场确认并入手册，不自动迁移）；变更操作前读取
  （见 SKILL.md 红线 7）。与手册的分工：**「模块规则」章管「内容规则」
  （什么进哪个模块、怎么分），「agent 约束」章管「agent 行为」
  （插件、额外红线）**——都在用户可见可编辑的同一份手册里。
- **维护**：结构变更时更新用户手册相关部分，并写入 `.config/变更记录.md` 与
  当日日记（单篇归档等常规操作只进日记，不进变更记录）。

## 模块发现与登记（v3 核心机制）

- **发现时机**：每次对话前置扫描一级目录；每次入库、分类、沉淀、整理操作前，
  对照 **config `preferences.modules`（机器索引）+ 用户手册「模块规则」章节
  （规则正文）+ 库中实际存在的一级文件夹**。三者对不上即触发问询：
  - 库里有而未登记的目录 → 新模块待登记；
  - 已登记而目录消失 → 待注销；
  - 手册有而目录/config 没有的 → 提示漂移，现场对齐。
- **登记流程**（agent 执行，全程征得用户确认）：
  1. 发现未登记的一级目录（用户手建，或用户口头要求新增时 agent 先建文件夹）；
  2. 逐项询问（不一次性抛所有问题）：**装什么**（一句话职责）、**入库规则**
     （什么内容进、从收件箱沉淀时怎么判）、**分类规则**（内部怎么组织）、
     **命名约定**、**type 属性取值**；以模块准入五条件把关；
  3. 写入**用户手册「模块规则」章节**新增一节（规则正文的唯一落点）；
  4. 写入 config `preferences.modules`（目录名、模块名、type）；
  5. 编号：建议**保持「系统/归档末两位」的编号方案**（必要时含系统/归档的
     顺延重命名清单，一次执行并同步 config/手册/看板/日记配置）；用户坚持
     自己的编号时以用户为准（此时结构校验会提示与规范不一致）；
  6. 看板补视图；当日日记（agent 章「系统」小节）记录；结构性调整另记
     `.config/变更记录.md`。
- **未登记状态下的行为**：未登记目录里的内容**不动、不整理、不判错**
  （`vault_check` 只出 warning）；用户明确要求操作其中内容时按通用红线执行；
  入库/沉淀的目标模块未登记时，先走登记流程再执行，不静默写入未知目录。
- **注销**（用户手动删除某模块文件夹时触发）：agent 发现已登记模块目录消失 →
  **询问用户是否在用户手册里同步删除该模块章节**（二选一：同步删除 / 标注
  停用保留历史，以用户选择为准）→ config 移除登记 → 看板移除对应视图 →
  变更记录必记。

## 模块流程（通用机制）

### 00 收件箱（捕获入口）

- **形态**：平铺，无子目录。文件名 `序号-内容简述.md`；序号＝当前收件箱最大
  序号＋1，两位补零，超 99 自动三位。**只有 `数字-` 开头的 md 文件计入序号**
  （待审阅文件、用户手写文件不参与序号计算）。沉淀后序号稀疏属正常，不回压
  重编（重编会断引用；序号只承担「到达顺序」一个职责）。
- **写入两条路**：
  - **agent 写入**：全套规范照做（属性与命名见 `references/properties.md`），
    为用户浏览时一眼可读；
  - **用户手写**：零要求——无属性、无序号、名字随手起都行。
  这就是**宽进严出**：规范约束的对象始终是 agent，不是用户的动作；门槛不长在
  用户这一侧。
- **校验豁免**：收件箱是校验豁免区，用户手写文件永不判「不合格」。校验是
  出门（沉淀）时的事。待审阅文件同在豁免区，且被沉淀流程明确跳过（见
  「写入审计闭环」）。
- **审阅沉淀（严出，用户发起）**：逐条过，去向由内容定——
  1. 按手册「模块规则」判定归属模块的（如摘抄、经验结论）→ 进入对应登记模块；
  2. 不再活跃 → `04 归档/<归档当日日期>/`；
  3. 无价值 → 删除（进系统回收站）；
  4. 仍不明确 → 留下。
  沉淀时补全：缺 `created` 用文件系统创建/修改时间，缺标签类型按内容补；
  沉淀后删除**已离箱条目**（去向 1–3）的原收件箱文件（流程内变更，按红线 2
  执行）；去向 4「留下」的原文件保留在收件箱。**待审阅文件不是内容条目，
  沉淀时跳过**。
- 随身端与暂存库条目的入库见 `references/desktop-ingest.md`。

### 01 知识（验证过的）

- **定位**：跨项目验证过的经验与结论（晋升而来），以及用户主动收录的理解类
  内容。**按主题组织**——一个主题一份文档；不按用途或抽象程度分类。动机：
  主题轴是用户真实的心智轴，写入与查找都不需要背规则。
- **起步**：初始化后本模块为空；首次写入时按 `03 系统/模板/主题文档模板.md`
  的形状创建主题文档（形状见下条「文档形状」）。
- **文档形状**：属性载体是主题文档本身；「章节（`##`）→ 编号段落」——每段
  用「一、二、三、」编号，一段写一条经验或结论，写清结论、动机与背景；单章
  超过约 30 段时提议拆分。**正文 = 用户原话完整记录**（原话如何说就如何记，
  不提炼、不改写、不压缩、不存对话概要，不分「原话」和「补充」）；agent 需要
  补写背景或动机时经用户同意后作为后续编号段落写入，不默默加，遵循「记录
  质量把关」。
- **章节/主题命名**：名字自解释就不加说明（如「架构设计规范」）；不自解释的，
  标题下一行补使用场景（如「用户提示词规范」下一行：这是给用户设计提示词的
  时候用的）。判据：光看名字能不能知道什么时候用。
- **条目合并**（含晋升进库的条目）：收到条目与主题 → 创建前相似检查（红线 5）
  → 有该主题文档则找到章节合并（章节没有就加），没有主题文档则新建 → 日记
  记录、核验。**同名冲突**：库内存在多份同名主题文档时（如平铺一份与拆分
  文件夹内一份），不猜，交用户定夺。条目晋升的时机与判据在库外（项目侧）
  定义，本库只管接收合并。
- **新建主题**：低风险，直接建，随后记录并告知用户。
- **章节涨破拆分（先单体、涨破再拆）**：单章段落超过约 30 段时，提议把该章
  拆成独立文档，原主题文档升级为同名文件夹收留。命名约定：文件夹＝主题名；
  主文档保留原名移入文件夹（如 `架构设计/架构设计.md`，保留其余章节，顶部
  列出拆出的章节文档链接作导航入口）；拆出的文档以章节名命名
  （如 `架构设计/大章节.md`）。拆分涉及移动文件，**先展示方案、征得同意后
  执行**。这是知识模块唯一的生长方式，不提前设计层级。

### 扩展模块（登记制）

- 一切已登记扩展模块（如摘录）的入库、分类、归档、拆分等规则，**按用户手册
  该模块节执行**；手册该节写不明的地方，问用户，不猜。
- 模块内部的分类集合、聚合与拆分阈值（如「超 N 条拆分」）属于该模块的规则
  正文，登记时与用户确认，写在手册模块节里；不在 skill 内写死。

### 04 归档

- 所有模块（收件箱、知识、扩展模块等）都可归档；
- 文件夹按**归档当日日期**命名：`2026年08月09日/`（中文补零）；
- 单篇文件平铺；文件夹整体归档时保留原文件夹名；
- **懒加载创建**：首次归档时先创建 `04 归档/<归档日期>/`（目标目录不存在时
  先创建再移入），归档后即可见；
- GitHub 暂存库同步入库的源文件归档在暂存库 `<folder>/归档/<入库日期>/`
  （见 `references/desktop-ingest.md`），本地归档不重复存放；
- 归档动作记入当日日记；**结构性调整**（如整目录批量调整、模块级变化）另记入
  `.config/变更记录.md`，单篇归档不记变更记录。

## 写入审计闭环（agent 内容写入的账）

**触发范围**：agent 的内容写入类操作——入库、沉淀、合并/晋升、移动、归档、
删除。低风险运营动作（日记补记、看板微调、导出、配置维护）不建待审阅文件，
日记照记。

每次触发范围内操作后，两笔账都必须记：

1. **日记**：当日日记 agent 章对应小节，详细记录（对象、动作、去向、依据），
   不是「更新了某文件」一笔带过；
2. **待审阅文件**：`00 收件箱/待审阅-YYYY-MM-DD.md`（**不带序号**）——
   - **一批操作/一次对话一份**，同日多批追加更新同一天文件；对话跨天时按
     写入当刻日期走当天文件；
   - 内容：本批动作清单——写入/修改/移动/归档/删除了什么、各在哪里看、
     有什么链接变化；开头一句「审阅后可删除本文件」；
   - frontmatter 带 `type: capture`，自然出现在看板「收件箱-待沉淀」视图；
     **用户删除文件后，视图中该行自动消失**（Bases 实时查询）；
   - 不参与 HTML 导出（默认排除）；沉淀流程跳过；收件箱序号计算不含它；
   - **清理**：用户审阅后自行删除，或对 agent 说一声由 agent 删（进回收站，
     记日记）；agent 不主动清。

## 日记（＝操作记录）

- **遵循 Obsidian 本身的日记规则**：日记由核心插件 **Daily notes** 管理
  （文件位置与日期格式按插件设置；年切分用日期格式 `YYYY/YYYY-MM-DD` 实现，
  即 `03 系统/日记/YYYY/YYYY-MM-DD.md`）；agent 追加日记时写入 Daily notes
  约定的当日文件，不存在则按插件格式创建；初始化时引导配置 Daily notes。
- **每日一文件，分两章**（按记录者划分）：

  ```markdown
  # 2026-08-30

  ## 用户

  （用户亲手记录的条目；用户让 agent 代记的自己的话也记在此节。当日无内容留空。）

  ## agent

  ### 入库
  - 15:30 入库 3 条至 00 收件箱（08-xxx、09-xxx、10-xxx，来源：GitHub 暂存库）；
    详见 00 收件箱/待审阅-2026-08-30.md

  ### 补记
  - 14:20（推断）用户修改了 01 知识/阅读与笔记法.md：新增小节「卡片盒」；
    依据：git diff（或文件修改时间；推断不出具体内容时只记「检测到改动」）

  ### 沉淀 / 整理 / 归档 / 删除 / 系统（按需使用）
  ```

- **agent 章固定七小节**：`入库` / `沉淀` / `整理` / `归档` / `删除` / `补记` /
  `系统`（沉淀＝收件箱审阅去向判定；系统＝模块登记/注销、配置与手册维护类
  动作）。小节不存在时创建。
- **详细度**：agent 章每条写清改动了什么（对象、动作、去向、依据）；与待审阅
  文件互为索引（日记行指向待审阅文件，待审阅文件列明细）。
- **补记**：用户的改动常无日记——agent 整理/运营时发现无记录的变更，依
  **文件改动历史与 git**（vault 是 git 仓库时；「不代为 git init」红线不变）
  推断并补记，注明「推断」与依据；推断不了具体内容的不臆造，只记「检测到
  改动」，必要时问用户。
- 日记就是库的操作记录：agent 章由 agent 自动维护，用户章随用户自由使用，
  随时可以翻——它回答「某天我对这个库做了什么、谁做的」。
- 日记**不参与看板聚合、不参与 HTML 导出**。

## 操作后流程（每次写入 / 修改 / 移动 / 删除 / 归档后执行）

1. 写日记：当日日记 agent 章对应小节追加详细记录（见「日记」）；
2. 待审阅文件：内容写入类操作建/追加当日 `待审阅-YYYY-MM-DD.md`
   （见「写入审计闭环」）；
3. 建立双向链接：沉淀/归档/相关笔记之间建立链接；
4. 插件规则：按用户手册「agent 约束」章配置的规则执行（如版本提交、同步）；
5. HTML 镜像导出（若配置 `exportEnabled=true`）：写入/修改 → 单篇导出；
   删除/移动 → 全量导出（含清理）；
6. 看板反映确认：看板已启用时确认实时反映正确；
7. **核验**（结构面与语义面）：
   - **结构面**（属性可解析、必填属性、type、命名）：优先运行库内
     脚本 `vault_check.py`（见 `references/init-config.md` 「脚本一览」），
     扫读其输出的每篇键值摘要；**收件箱路径豁免、非 md 文件跳过、未登记
     目录只警告**；脚本不可用时人工回读。批量写入（≥3 篇）时脚本核验全部
     条目并抽 1 篇全文回读；单篇写入仍全文回读；
   - **语义面**（内容正确性、原话完整、双向链接指向、日记记录、待审阅文件、
     插件规则与 HTML 导出执行情况）：由 agent 逐项核对；
   - 发现缺失立即补正并告知用户；
8. 反馈：写入位置、建立的链接、待审阅文件位置、后续建议。

## 通用操作规则

- **职责边界**：agent 只做**格式整理＋系统运营＋按用户指令的内容写入**；不
  主动代运营内容——不自行决定写什么、不自行扩充或改写正文、不无指令地往
  主题文档塞内容。动机：内容是用户的，agent 是整理者与执行者，越俎代庖会
  污染用户的思想留痕。
- **原话完整**（一切记录与入库）：**不得改写、不得压缩用户原话**，用户原话
  完整记录（原话如何说就如何记，不分「原话」和「补充」）；agent 的补写说明
  按用户要求添加，或提议经用户同意后写入，不默默加。动机：原话是用户的思想
  留痕，改写即失真；「记录质量把关」约束 agent 的补写与整理，不作用于原话。
- **写入前健康检查**：要写入某个既有文档（主题文档、模块聚合文件等）时，
  先扫一眼全文，发现不符合规范的现象（多为用户手改痕迹），**先问用户「要不要
  先按规范整理，再写入新内容」**——不默默代改，也不踩着乱处直接写。
- **点名整理**：用户明确指出某文档动过、需要整理时，直接执行；库是 git 仓库
  时可用其差异信息辅助识别用户改动（不代为初始化仓库的红线不变）。整理与
  运营中发现无日记记录的用户改动，按「补记」规则帮用户记入日记。
- **记录质量把关**（agent 的补充说明与整理行为要求）：详实通俗——写清前因
  后果、背景与动机，保证用户看懂；不刻意追求专业性，为看着专业牺牲通俗是
  不应该的；不为省字写得过简；必要时用正常的日常化举例、比喻；**不精简用户
  提供的信息**，禁止「一句话说明白」式压缩——一句话本身就很难说明白；语言
  质量要高，无 AI 味（怪异比喻、不常见表达与举例一律不用），保证很久以后
  读来仍能充分理解。本条不作用于用户原话（见「原话完整」）。
- **兼容容忍**：用户自建的白板（`.canvas`）等非笔记文件是用户的自由空间——
  不主动整理、不校验、不导出、不报错；用户要求操作时按相应工具规范执行。
